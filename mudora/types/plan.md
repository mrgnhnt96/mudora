# Plan pages

**Marker:** `<meta name="mudora-type" content="plan">`
**Starter:** none yet; reuse `starters/base.css`

A plan is an overview to understand the problems and what will be done to fix them. It's not a tracker. A plan that also links out to the pages behind it (a hub) lists each linked page with one line on what it answers.

## Rules

- **No ticks or saved state on plan pages.** A plan is an overview to understand the problems and the fixes. Don't add checkboxes, progress counters, "clear ticks" buttons or anything stored in the browser. Plain lists instead. One exception: open questions for someone else (for example "Decisions needed") are answerable cards that save to the page's shared storage and show who picked what by name. Make them intuitive: phrase each as a real question, keep every bit of the original context visible and labelled ("Why it matters", "Who decides"), and answer with taps, not typing. A yes or no question is a single check mark, a choice is a set of option buttons (tap again to clear), a "which of these" is a checklist. Choice and checklist questions end with an "Other" option that opens a box for the person's own thoughts, shown to everyone with their name. No other text boxes.
- **Long lists grouped into areas: a plain overview of problems and fixes.** For an inventory such as a screen list, show one row per area: the area's name, then "The problem" and "The fix", each one short line of about ten words, side by side on wide screens and stacked on phones. Keep it calm and plain: not curt, not technical. The full item list can sit below in one closed section, as a simple bulleted list grouped by area. Don't use card pickers, a summary table followed by collapsed sections that repeat the same areas, or wide tables of six or more columns.
- **Tag each task by where it belongs, not by the quickest route.** On a plan for a test framework, anything that acts on the app the way a person would (finding, tapping, scrolling, turning the device) is a framework step, even when another tool could do it through a script step. Tools beside the framework handle what's around the app: builds, installs, ports, networks, test servers.
- **Lede:** background about the work and what the plan does, at most three and a half lines (rule 29). Don't explain a product to the team that builds it.

- **No waves, sizes or step order.** Readers care what the plan delivers, not how the work will be scheduled: no wave chips or wave legend, no S/M/L sizes or other effort marks, and no "after N" notes on steps. No status chips on steps either ("Next in line", "Waiting for review"): a single step carrying one looks out of place among the rest.
- **A goal's intro covers the whole goal.** The paragraph under a goal's name says what the goal as a whole fixes, touching every group of its steps, not one step's problem in detail (a goal of twelve steps doesn't open on the scroll timings of three). It says what's wrong today, not the order the work happens in. The goal card carries no row of places or projects either; each step's own tag already says who picks it up.
- **Each goal ends with a closed "How it's used" section.** One line on who uses it, then a few short highlighted examples (a test file, the commands people run, a config file) showing the feature in use. Mark every line that doesn't exist yet with a trailing `-- planned` or `# planned`, check every other line against the code, and close with one line saying what works today. Keep code comments short so a line fits the block on desktop.
- **Example settings explain themselves.** In a config or environment-file example, every key says exactly what it sets (`app_starts`, not `phone`), and a short trailing comment lists the other choices. A setting that can take several values (devices, permissions) is shown as a list with two entries. Name each device the way the tool picks it (an emulator or simulator by name, a real Android by serial, a real iPhone by device ID), and keep the example to combinations the plan says work. When one setting forces another (an iOS simulator needs `app_starts: fresh-install`, because removing the app is the only way to reset its permissions), say so in a comment beside that setting and have the schema check refuse the combination that breaks it.
- **Example commands say what they do and carry a fitting name.** A command whose name doesn't say what it does (`apply`, `up`) gets a comment line for each thing it does, in order. Name a planned tool for the widest thing it serves, not after the narrower tool it grows from or the one app it starts with: a test setup tool is named for the test framework it serves, not for the first app that uses it, since any app on that framework can use it. Planned commands belong to that one tool (`testkit up --device "iPhone 16" --car-screen`), not a new tool per feature, and pick devices the same way everywhere (`--device`). When the plan has a settings file for a setup, every later goal's setup goes in that file too (a car screen is a device setting), and its examples set up through the file rather than one-off flags. An example never makes the reader start something by hand that the tool could start from what it already knows (a run starts the tap helper for the device it runs on); if a manual step is needed today, the plan has a task to remove it and the note says why it exists. When an example needs a device the reader may not expect (a phone simulator for a car-screen test), a comment says why.
- **A planned file format comes with its schema.** When the plan adds a file people write by hand (an environment file, a settings file), the task that adds it also adds a schema for it, so editors flag mistakes as you type and the tool checks the file before using it. Say so in the task and show the check in its example.
- **Linked research goes at the end.** The list of pages behind the plan sits after the goals and the limits, just above the closed detail sections, never near the top. Readers want the plan first; the research is there for whoever wants to dig in.
- **No time estimates.** Leave days and weeks off plan pages: no estimate on a goal header, a summary card, a timeline row or a hover tip. Only add time estimates when the user asks for them.
- **Goal headers stay in view while you read the goal.** A goal card's header (number and name) is sticky just under the page's top bar until the card ends, so a reader deep in a long goal still sees which goal it is. Give it the card's own background and stretch it to the card's edges so steps slide under it cleanly.
- **Don't ask what the tools can decide, and don't cap what QA does.** Leave out open questions about details a tool can settle by itself (which port a device gets: the next free one, recorded where everything reads it) and limits on QA's own choices (how many devices run at once, which environments exist: QA writes their own, the plan supports any). Variations of a test aren't generated (no automatic run in every orientation): QA copies the test and points it at another environment. Once the user answers a question, fold the answer into the goal's steps and drop the card; when none are left, drop the section.
- **Every goal ends with handing it to the people who use it.** The last step of each goal is the hand-off: the work in the package they install (for QA, the test package), any app change in a build they have, a guide page or what's-new note, and them running one of their own cases with it. Tools they run must install without a developer checkout. Don't describe the hand-off in the goals intro: the step itself shows it. An intro says only what the reader can't see in the goals that follow.

## Checklist

- Are there no ticks, progress counters or saved state, other than answerable decision cards?
- Is each area one row with a short problem and a short fix?
- Does each decision card keep its context visible and answer with taps, with an "Other" option on choices?
- Does every linked page get one line saying what it answers?
- Are waves, sizes, step order and goal-level place labels left off, and does every goal have a closed "How it's used" section with planned lines marked?
