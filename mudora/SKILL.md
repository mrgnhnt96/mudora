# Mudora: artifact pages people can read

These rules came out of reviewing many real pages. Follow them together with the Artifact tool's own design guidance, which still applies (quickstart, the page contract, theming). When they conflict, these rules win, and the user's own word beats both.

The rules live in layers. Read this file, then the one type file for the page, plus the shared files it points to:

| File | Holds | Applies to |
|---|---|---|
| `SKILL.md` (this file) | Rules for every page, how to work, where feedback goes | Every page |
| [components.md](components.md) | Option cards, chart behaviour, interactive pieces | Any page that has that piece |
| [charts.md](charts.md) | Which chart for which question | Any page with a chart |
| `types/<type>.md` | The shape, variants and review checklist for one type | Only pages of that type |
| `starters/` | HTML to start research, results, evidence and design-doc pages from; one shared style (`base.css`, copied in by `sync_css.py`) | New pages |
| [pages.md](pages.md) | Every page, its type and its link | Lookup |
| [corrections.md](corrections.md) | The user's words for every correction, and the file each went into | History |

When a type file and a general rule disagree, the type file wins for that type only.

## Which type is this page?

Pick the type before writing anything, start from its starter, and put its marker in the page's `<head>`: `<meta name="mudora-type" content="<type>">`. The marker is how a later session knows where feedback on the page goes.

| The page… | Type | Guide |
|---|---|---|
| asks whether something can be done and how, with options and follow-up work | `research` | [types/research.md](types/research.md) |
| is research written for the team to decide on, recommendation first | `proposal` | [types/research.md](types/research.md) |
| reports what a measured change did, numbers first | `results` | [types/results.md](types/results.md) |
| answers one yes/no or "does it still hold" question | `check` | [types/results.md](types/results.md) |
| reports numbers from a source the team doesn't control (crash dashboards, store data) | `data-report` | [types/results.md](types/results.md) |
| shows a fix working, with before and after pictures | `evidence` | [types/evidence.md](types/evidence.md) |
| designs a change: problem, solution, risks, testing | `design-doc` | [types/design-doc.md](types/design-doc.md) |
| gives an overview of problems and the work to fix them, or links a set of pages | `plan` | [types/plan.md](types/plan.md) |
| is presented to people in 10 minutes or less | `presentation` | [types/presentation.md](types/presentation.md) |
| is a slide deck | `deck` | [types/deck.md](types/deck.md) |
| explains how something works | `explainer` | [types/explainer.md](types/explainer.md) |
| lists what changed, or hands a change to QA | `whats-new` | [types/whats-new.md](types/whats-new.md) |
| tells someone how to do something themselves | `guide` | [types/guide.md](types/guide.md) |
| collects comments or approvals from several people | `review-tool` | [types/review-tool.md](types/review-tool.md) |

If none fits, use the closest one and tell the user in one line; if a second page of the new kind comes along, make it a type of its own (a new file in `types/`, a row here and a starter).

**One page per subject.** Before publishing a new artifact, check [pages.md](pages.md) for a page on the same subject. If one exists, update it at the same link (republish, with a label) rather than starting another; a follow-up result is a new section or a refresh of that page, not a new artifact. Only start a separate page when the subject is really different, and say why in one line.

## Where the user's feedback goes

Every piece of feedback the user gives on a page, however small, is fixed on the page and written into the skill in the same turn, without being asked. The point of the layers is that a fix lands in the right one: not in every type when the user meant one, and not in one type when the user meant all of them.

1. **Find the page's type.** Read its `mudora-type` marker, or look it up in [pages.md](pages.md). A page with no marker gets one now.
2. **Decide how far the lesson reaches.** Read the user's words for scope, then pick the narrowest file that covers it:
   | The feedback is about… | It goes in |
   |---|---|
   | a fact, a typo or wording on this page only | the page only (log it as "→ page only") |
   | how this type of page is laid out or what it contains ("research pages should…", a section only this type has) | `types/<type>.md` |
   | a piece that appears on several types, wherever it appears (every option card, every chart, every review switch) | [components.md](components.md), or [charts.md](charts.md) for choosing a chart |
   | writing, tone, layout or honesty on any page ("never…", "always…", "any page…") | "Rules for every page" below |
3. **When the scope is unclear, go narrow.** Put it in the type file and say so: "Added to research pages only (types/research.md); say if it should apply to every page." Don't widen a rule to every page on a guess. If the same lesson later comes up on a second type, move it up to components.md or the general rules and delete the narrower copies.
4. **Rewrite, don't stack.** If the feedback replaces an older rule, rewrite that rule where it lives, and remove any copy of it in another layer. Search the skill for the old wording first (`grep -rn` across the folder) so no conflicting copy survives.
5. **Update the starter** when the rule changes how the page is built: the type's starter, or `starters/base.css` when the rule is about shared style, then run `python3 starters/sync_css.py` to copy it into every starter.
6. **Log it.** Add a dated line to [corrections.md](corrections.md) quoting the user's words, ending with the file it went into (→ `types/results.md`).
7. **Tell the user in one line** which file changed and for which pages: "Rule added to results pages (types/results.md)."

## Rules for every page

0. **Every doc is an artifact page from this skill, never a Claude Doc.** Plans, design docs, reports, QA handoffs, what's-new notes and guides are all pages published with the Artifact tool from this skill's rules and templates. Don't call the docs connector (Claude Docs `batch`, `update`, `create`), even when the user says "doc", even when the docs skill says it is the default, and even when the page is for someone else to read. Only use Claude Docs if the user names Claude Docs.
1. **Show the minimum needed to understand the problem and the solution.** Aim for a page that can be read in a few minutes. Cut anything that repeats: a "top five" section that restates findings shown later was removed. The page tells one story, and each section moves it forward. Before keeping a section, say in one line what it teaches the reader and which decision it supports. If you can't, cut it or fold its one useful number into the section that needs it. A set of measurements that are true but don't answer a question is not a section.
2. **Keep the visible text non-technical.** The explanation has no class names, file paths, line numbers, code identifiers or tool names. Say what something does ("the old main screen", "one cleanup list", "the performance tools"), not what it's called in code.
3. **Collapse code and technical detail.** Code, file-by-file tables, raw measurements and full checklists go in closed `<details>` sections below the plain explanation. Never put them inside the explanation itself. Summary labels are plain names, with no "(technical)" tags.
4. **Keep the tone matter-of-fact.** Don't be dramatic, don't use power statements, and keep it slightly informal. The page informs; it doesn't sell. Say what something is, not what it isn't: leave out defensive caveats such as "so they don't add up". If a sentence exists only to stop the reader misreading something, fix the thing instead.
5. **Include only what was actually done or measured.** Don't bring up work that wasn't done, estimates from things that weren't measured, or anything not on the main branch: uncommitted changes, reverted test builds, local-only notes.
6. **Move code locations out of the body.** If they're needed, list them as numbered references at the bottom and point to them with superscripts.
7. **Mention the setup once, at the bottom, collapsed.** Explain things like the devices, debug and profile builds, or which tool measured what, once in a closed "Setup" section near the end of the page (just above the references). Readers don't need it up front. Don't repeat it on every chart or row.
8. **Fact-check before sharing.** Every claim about the code must match the code. A presentation gets a full fact-check pass against the source. On every revision, check each risk, cost and open item against what has since been done, including what the page's own setup notes say, and drop the ones already handled.
9. **Watch the layout.** Fix clipping and overflow. Don't repeat labels ("Android Android"). More broadly, no label, caption, tip or toast repeats what the reader can already see next to it: the chart's name, a row label, a value printed on the mark, or a message already on screen. Say only what is new. Code blocks get syntax highlighting. Closed sections stacked one after another sit close together as one group, not at the full gap between sections.
10. **Don't use internal codes or words coined during the work.** Finding numbers (F7), option labels (R1) and similar shorthand confuse readers who haven't seen the index. Use plain names ("the image listener fix", "building the tab navigators once"). Numbered rows in a table the reader can see are fine. The same goes for words that became familiar while doing the work, such as "pair", "hop", "layout" or "agent time": a reader studying the page won't know them. Use words that explain themselves ("a main-branch run and a combined run started at the same moment"), or define the term in one line where it first appears. Reread the page as someone who wasn't there and list every term that only makes sense from the experiment.
11. **Include a real-app example.** Numbers from a test script are easier to follow when a short, everyday path goes with them, for example "open the app, go to Search, pick a result, save it". Say what happens on that path.
12. **Paint the picture with images, not text.** Where something can be shown, show it, and keep the text short beside it. For example, a device setup is a simple generic drawing of each phone (iPhone, Android) or simulator with a caption, how it was connected (a cable, Wi-Fi, or running inside a Mac window), and the details as a few bullets to the right of the picture. Don't go so far that the meaning or context is lost: keep the facts the reader needs next to the image.
13. **Put measurements in charts, not tables.** A table of timings is hard to compare. Pick the chart from the question the numbers answer, using [charts.md](charts.md) (catalogue, when not to use each, and a decision guide). Values that span a wide range go in separate panels by size, each with its own scale. Label values directly on the marks: inside the bar, or just past the end of a short one, never in a column at the far right (see charts.md). Don't repeat the chart as a table; if the raw runs matter, one closed "Every measurement" section is enough. A chart exists to make numbers or flows easier to grasp, not to break up the text. If the text has to explain how to read the chart ("the bars share one scale, but each covers a different part"), it's the wrong chart: pick another form, or split it, until it reads without help. The same goes for numbers written out in prose: a before-and-after ("went from 68–71 to 31 minutes", "52 to 35 minutes a run") repeated row after row belongs in a small mark that shows both values, with the unit stated once, not in a sentence on each card.
14. **Don't write walls of bullets.** Turn lists such as limitations into short tiles grouped by device or area: a bold headline of a few words, one line under it, and a small icon for the kind of item (can't, work-around, good to know, not done yet). Fold the "not tried" items into a row of small chips.
15. **Show only what's needed, and push the rest to hover or small text.** For setup, install or requirement lists, ask what the reader actually needs to do. Show that as a short path of steps; put versions, commands and sources in a hover tip or small grey text; drop rows nobody acts on (things every Mac already has, tools installed by another tool); drop a step's sub-label when it only names the script or tool behind it (that belongs in the hover tip), and drop "no X needed" lines that only contrast with another card. Install cards get no footnote by default: caveats like signing keys or "remove the old app first" are left out unless the user asks; don't add extra closed sections under it either: no "build it yourself" tool list, no "commands that were run". The hover tips are enough.
16. **Draw step-by-step flows, don't write them.** Real-app examples, test paths and any "did this, then that" go in a flow diagram: one row per test, screens as soft borderless pills with a two- or three-word name, joined by thin arrows with a small grey action label of two or three words (solid for a tap, dashed for a swipe), and a quiet "✓ 3 of 3" at the right end of the row. No legend, no "where" labels, no dividers; extra detail (timings, setup) goes in a hover tip on the result. Leave plenty of space between rows and inside cards so it feels calm. Keep each row on one line on desktop; on a phone, stack it top to bottom.
17. **Make it feel calm.** Dense blocks feel busy even when every word is useful. Give cards and rows generous space, drop borders, dividers and legends that the content already explains, use soft fills over outlines, keep labels to a few words, and move secondary detail into hover tips. If a section looks packed, cut words before shrinking text.
18. **Say why one result differs from another.** When a device, build or run is slower or behaves differently, name the cause on the page in plain words, for example "the simulator taps faster because it runs on the Mac, not over Wi-Fi". Check it before writing it (for a build, which release tags include the feature), and put it where the slower number appears, not only in the setup. A gap that goes away on its own once something ships (a feature not in a release yet) stays out of the TL;DR: it's a non-issue for the summary.
19. **Every card gets a title, and summaries stay to one line a row.** A card with no heading leaves the reader guessing what it's for, so the summary card is titled plainly "TL;DR", not a made-up phrase like "The short version". The TL;DR has at most five rows: pick the findings that matter most to a newcomer and move the rest into their sections. Each summary row is one short sentence, about 15 words; build details, caveats and how-tos live in the sections below, not in the summary. Every row is a finding a newcomer gets value from. Each row is one finding: if a row joins two clauses, the second must add to the first, not sit beside it (split it, or drop the half that adds nothing). Leave out how it was measured, the order to ship, and anything that reads as a plan rather than a result. Say plainly what a number is: a measured result ("tried together, the changes cut a run from 47 to 29 min"), never wording that could mean the result after a fix ships. Name the thing in everyday words ("two downloads repeat on every run"), not by its fix ("a pinned Android tool").
20. **Name the things, don't count them.** Never write "all three devices" or "all three"; say which ones ("a real iPhone, the iOS simulator and the Android emulator"). The reader may not have seen the list the count refers to.
21. **Labels say where, and say how.** A step label names the place it happens, as a bare noun with no "in" or "from" and nothing extra ("The team's Apple developer account", "TestFlight"), not a vague action ("Install from the Mac"). Where it comes from goes in the hover tip. Name each option by who it works for, not by contrast with the one before it: "Any phone", not "Other phone". When a step depends on something being set up (a registered phone, an account), say how to set it up right there in one line, not only that it's needed.
22. **Try every cell before calling it "not tried".** A results grid (device × build, step × device) is a promise to cover each combination. Before publishing, try every cell that's within reach: build the missing mode, pull a build from CI's bucket, install it on a free device. A cell may only say "not tried" or "doesn't apply" with a concrete blocker in it (a sign-in only the owner can do, a tool that refuses, a permission that was denied), never "no build was made", and it names the closest thing that was tried instead.
23. **Name rows by kind, not model.** Row and column labels say what kind of thing it is ("Real iPhone", "Real Android", "Android emulator"), matching the other rows; the exact model goes in the Setup section.
24. **Keep work-tracking terms off the visible page.** No ticket, task or backlog ids (PROJ-123, T192, B326), and no names of the tools or terminals the work ran in, in visible text, chips, titles or hover tips. Put them in hidden metadata instead (an HTML comment or a `data-ref` attribute) so an agent can still trace each item. Describe the item in plain words for the reader.

25. **Say plainly what an open item is missing.** For something not done yet, say what hasn't been tried and why the obvious route doesn't work, using what was measured ("no way to record it has been tried yet; screenshots at 1.4 s each are too slow for video"). Vague wording like "hasn't been picked yet" leaves the reader guessing whether a choice is pending, between what, and who makes it.
26. **Headings make sense on their own.** A reader skimming the page sees only the headings, so each one says what the section shows: "Savings from each change, tested separately", not "Each idea on its own". Test it by reading the heading alone: if it could mean several things, rewrite it.
27. **Don't signpost.** Leave out "further down", "shown below", "see the section above" and similar pointers to where things appear. They distract from what the paragraph is saying. Pointers belong only in an index, or in a section whose job is to guide the reader.
28. **Leave out sign-offs and who said what's OK.** "The lead approved this on 21 October" helps no one: one person's OK doesn't make it OK for the reader. Don't mention approvals, who agreed, or when, on the page.
29. **Title the page for a reader with no context.** The title, eyebrow and lede say what the page is about in plain words, not the name the work went by while it was being done ("Build Findings", "Faster builds"). The lede gives the one line of background about the work itself that a newcomer needs before the rest makes sense. Don't explain the product to its own team: on a plan or report for the people who work on a product, the lede doesn't say what that product is; link its own docs instead if background might help. Keep the lede to at most three and a half lines on desktop (about 280 characters): background and what the plan does, not a list of everything it covers. Keep the subject itself in the title (CI, the mobile app), and spell out any acronym once in the lede: making the title plain must not drop what the page is about.
30. **Give the page some personality, without being drastic.** Calm is not plain. Use a soft colour glow behind the page, a frosted-glass header and tooltip (a backdrop blur), shadows that lift a card a little on hover, and a small colour accent on section headings and step numbers. Keep it to a few touches: the content stays the focus, and every colour still means one thing (charts.md).
31. **Don't mark what changed between versions.** No "changed since the first version" dots or keys, no "what changed" section, no "now" or "no longer" comparisons with an earlier draft. The page states what is true today; readers who care about the history can ask. Add it only when the user says the history matters for that page.
32. **A page about what changed covers only what changed.** A what's-new, release-note or handoff page lists the changes and how to get them. Limits, open items and coming-soon work are left off it, both in the TL;DR and in the sections, unless the user asks for them. The TL;DR rows are findings about the page's subject, so a how-to such as "how to update" never gets a row there; it lives in its own section.
33. **Every intro line gives the reader something.** A line under a heading gives the one thing the reader needs that the content below doesn't already show, in one short sentence ("Existing tests carry over, but a syntax error now stops the run"). Don't list what the steps or tiles under it already list. The line must be about that section's own subject (an install section's intro is about installing, not about how tests behave afterwards). If no such line exists, the section has no intro. Filler such as "Do this once" or "your tests stay as they are" gets rewritten or cut.
34. **Don't write to "you".** A page is read by people the writer doesn't know, so "problems you reported" or "the first build you get" leaves the reader asking who "you" is. Name the thing instead ("problems from earlier testing", "older builds don't have it").
35. **State limits as plainly as possible, and check status claims with the user.** "Real iPhones can't record yet", not "a real iPhone only gets a warning". Don't say a build will never have something when it is only waiting for a release (store builds get it once it ships); on a what's-new page, leave out the gap (rule 32).
36. **No open questions on the page unless the user asks for them.** The page gives answers, not questions for the team. Don't invent questions for readers to answer; if something is unsettled and the user can settle it, ask the user in chat, then write the answer into the page. Only add a questions section (or answerable cards, see types/plan.md) when the user asks for one.

## How to work on a page

- **Start from the type's starter** in `starters/` (copy it to the scratchpad and fill it in), keep its marker, and read the type's file before writing. Keep one doctype and one `<html>` per file, and never inline a large library (highlight.js and the like): load it from a CDN, or skip it.
- **Review before every publish.** Follow [review.md](review.md) before a page goes out. A fresh reviewer in a headless Claude (`review_page.py`, never a subagent, so it doesn't bloat this session) reads it as a newcomer and checks that every statement makes sense, the page flows, and each section brings value. The first version gets a full review. When the user asks for changes, the reviewer gets only the diff since the last reviewed version, plus what that change affects elsewhere, not the whole page. The reviewer only reports; the session that wrote the page decides each finding, fixes what holds up without asking the user, logs its decisions in the global [review-log.md](review-log.md), saves the published file as `<name>.reviewed.html` for the next diff, and tells the user in one line what the review changed. When the user asks to review a page by link, hand the findings to the session that last published it (review.md). Skim review-log.md's "Patterns" before writing a page.
- **Once the user gives direction, apply every fix.** When the user answers a set of proposed fixes, make all of them and publish; ask again only about facts only the user knows (which app a version is, who decides). Don't send the fix list back for another OK.
- **Update in place:** republish to the same URL, with a short label on each publish.
- **Save a backup first** before a big cut or rewrite, and say where it is.
- **Take removals literally.** When the user says remove a part, remove it along with its table-of-contents entry, and fix anything that pointed to it (section references, wording that relied on it).
- **Be willing to rewrite.** Sometimes the right fix is a full rewrite in a calmer, more matter-of-fact voice. It's fine to produce a v2 alongside v1 for comparison.
